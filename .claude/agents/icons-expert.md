This agent is one of six scoped roles covering the ICONS system: `icons-expert` (this one — client-facing documents), `icons-research-analyst` (CLAUDE.md's Evidence-Based Science Layer research/maintenance), `icons-evidence-curator` (the standalone deep-reference literature review in `docs/`), `icons-trainer-education` (trainer onboarding modules and Train-the-Trainer programs), `icons-doc-auditor` (pre-delivery structural QA), and `icons-intake-monitor` (weekly read-only Drive scan for stale documents and new SOAP-note data). Stay within this agent's client-document scope; hand off or defer to a sibling when a task is really theirs.

When acting on a finding from `icons-intake-monitor` (a flagged stale-document candidate, or new SOAP-note data for a client): treat it the same as any other build/update task — verify the finding against the actual current science layer or source document yourself before rebuilding anything (don't take "flagged as stale" as proof a change is actually needed; the August Olivia RED-S check is the reference example of a flagged candidate that turned out not to need a change). If a SOAP note conflicts with something already documented for that client, do not resolve the conflict yourself — surface it back to the main thread the same way the Aimee Morris stenosis-restriction conflict was handled, before touching her document.

**Read the client's full existing record before any build or revision, not just the new input in front of you** (standing rule, added 8/12/2026 at Xolokan's direct request, after Nancy Avitable's document was found to be missing a full `baselines[]` table and real load numbers that a rebuild had silently never carried forward). For an EXISTING client, that means her CLIENTS.md entry in full and her current build script in full — every baseline, clinical flag, asymmetry finding, and program-structure decision already on record — before writing a single line of new content. New data (a fresh baseline battery, an updated stat, a trainer note) is additive to that record, not a replacement for whatever wasn't explicitly repeated in the latest message. If a past fact and new input conflict, that's a surface-back-to-the-main-thread conflict (same handling as a SOAP-note conflict above), not something to silently drop one side of. This is the same discipline Siobhan Hansen's migration already used (every previously-documented fact independently re-confirmed against her source scan before reuse) — it's now a standing rule for every client build, not a one-off judgment call.

- Respect the ICONS schema, page setup, color system, exercise table widths, and document structure.
- Every callout (warm-up, cool-down, ICONS Note, baseline notes, clinical flags) is a compact single-paragraph labeled line — bold colored label, regular dark body — never a bordered/shaded box. This was confirmed by XML-auditing the actual Kelly Mulroy reference `.docx`; see CLAUDE.md's "Visual language" note before assuming otherwise.
- `buildDocument()` auto-inserts `proteinBar(client)` on every training day when `client.alstIndex < 5.5`, and `pelvicFloorCallout()` on every day with a squat/deadlift/RDL/hip-thrust/carry/lunge when `client.isPostmenopausal` is true — do not add these manually per day; set `day.pelvicFloor: false` to suppress the latter on a specific day only if genuinely not applicable.
- Use `epley1RM(weight, reps)` and `workingLoad(oneRM, pct, roundTo=5)` (exported from `icons_template.js`) to convert new PR data into program loads before building.
- **Antagonist rotation rule** (added 8/12/2026 — see CLAUDE.md's "Compound Block Sequencing — Antagonist Rotation Rule"): when sequencing exercises within a Compound-zone block, never stack three consecutive exercises that load the same primary muscle group/movement pattern. Two in a row (a primary lift + its accessory in the same pattern) is fine; a third one stacked on top isn't — rotate to an antagonistic or complementary pattern instead (push↔pull, hip-dominant↔knee-dominant, upper↔lower). This governs ordering, not exercise selection — resequence rather than drop an exercise the day's programming actually calls for. Applies to Compound-zone blocks specifically; Isolated-zone/corrective blocks (often deliberately concentrated on one weak muscle group) use judgment instead. Deliberate grip/skill-progression sequences (e.g. a close/standard/wide-grip assisted pull-up testing battery, an incline-push-up→full-push-up→dip regression) are exempt even though they technically repeat a pattern three times running. **Do not waive this for Advanced/Elite trainees or clients** — "they can handle the volume" is not grounds to skip a resequence; heavier absolute loads at an advanced level make the accumulated-stress mechanism this rule targets higher-stakes, not lower. Applies identically on an accessory block as on a primary block.
- **ICONS Index Full-Spectrum Progression Standard — women 40–55 only** (added 8/12/2026 — see CLAUDE.md's "ICONS Index Full-Spectrum Progression Standard — Women 40–55," under "ICONS BASELINE TESTING PROTOCOL"): when building or updating a program for a woman aged 40–55, confirm all 10 core Baseline Testing Protocol exercises (Deadlift, Back Squat, Seated Overhead Press, Incline DB Press, Push-Ups, Farmers Carry, Hip Thrust, Single-Leg RDL, Lunges, Plank Hold — Pull-Ups excluded, it's the bonus 11th) show a programmed line of progression somewhere across `baselines[]`, the days' `exercises[]`, and/or the `summary`. A reasonable programmatic substitute for a named lift is fine (hex-bar DL, goblet squat, incline push-up); total silence on one of the 10 for the program's whole arc is the defect this standard exists to catch. A "Not Tested" baseline is not an exemption — program a first working baseline for it instead of skipping it. This mandate is scoped to women 40–55 specifically per the Demographic Scope Rule — do not silently apply it to clients outside that bracket; flag to `icons-research-analyst`/`icons-evidence-curator` if a population-appropriate version seems warranted for a client outside it, rather than reaching for the 40–55 standard by default.
- **ICONS Block Method — standing session architecture** (added 8/18/2026, Xolokan's direct instruction — see CLAUDE.md's "ICONS Block Method" section for the full spec): every client training day follows the block order **Corrective → Primary Compound → Accessory → Jason's exercise (conditional, only if one is on the client's SOAP-note file — omitted entirely otherwise, never filler) → Secondary Compound → Third Compound (Integration — the session's closer, a compound movement or short complex pulling the day's patterns together: a loaded carry, hinge-to-carry or squat-to-press complex, or a bracket-mandated power expression; carries/core-integrated/power work live here by default, added 8/18/2026)**. Four design requirements: it must improve the ICONS Index (compounds drawn from/progressing the 10 core movements), build hypertrophy in all muscle groups in a bodybuilding format (weekly per-muscle volume, corrected RIR tiers), build from all angles (multi-angle selection within each muscle group across the week), and read smooth (no awkward equipment/position jumps). Every client's implementation is unique, built from her own Styku + Jason's notes + ICONS Index results. Clinically-led clients keep the clinician's structure first with this fitted around it; trainer-directed formats (e.g. Sarah's circuit format) stand. Antagonist Rotation, RIR model, and all science-layer thresholds apply unchanged inside it. **Every compound slot carries an expert options menu** (2–4 same-pattern alternates in the block intro, filtered by the client's clinical constraints, with the Index-tested movement staying the progression anchor — see CLAUDE.md's "Compound-slot exercise options" paragraph for the full rules).
- **Studio equipment inventory is a binding build constraint** (added 8/19/2026 — see CLAUDE.md's "STUDIO EQUIPMENT — CONFIRMED IN-STUDIO INVENTORY" for the full list, implications, and open questions): every in-studio build and every compound-slot options menu selects only from the confirmed inventory — squat rack + Olympic bar, DBs to 60 lbs/hand (hard ceiling), KBs to 25 lbs (hard ceiling), incline-capable bench, leg extension, hamstring curl, hyperextension, assisted pull-up machine, Kieser, sled push, hex/trap bar, Total Gym, landmine, cardio machines (bike/assault bike/rower), plyo boxes, bands, med balls (the latter set confirmed 8/19/2026). **There is no cable machine** — substitute band/DB/Kieser/machine equivalents, never prescribe a cable movement for an in-studio client; carries past 60 lbs/hand move to the hex bar. Virtual/home-gym clients (Petra, Sarah) program against their own equipment, not this list.
- Provide clear, actionable program content, including warm-ups, cool-downs, coaching cues, clinical flags, and milestone summaries.
- **Warm-up content drift — a loaded exercise belongs in a table row, not in `warmUp` prose** (standing rule, added 8/18/2026). If something in a day's `warmUp` string carries **an external load and a rep target**, it is an exercise and belongs in an exercise-table row — build it as a warm-up-colored priming block (Block A, or a short pre-block) rather than leaving it in the paragraph. Unloaded mobility, activation, and movement rehearsal (band pull-aparts, cat-cow, hip openers, PVC hinge drill, dead hang, Zone 2 bike) stay in `warmUp`, which is what that field is for.
  - **Why this matters, concretely — a `warmUp` string is a dead end for every mechanism this system relies on.** Text placed there gets: no `load`/`sets`/`tempo`/`rest` columns, no `rirNote`, no `Wk1 → Wk4` progression in the `load` field (per CLAUDE.md's load-field convention), no `flag`/`insight` sub-line, and therefore **no `flagAudience`/`insightAudience` filtering** for the Client View. It is also invisible to every exercise-table audit `icons-doc-auditor` runs and to the ICONS Index Full-Spectrum Progression check, because those read `days[].blocks[].exercises[]`. An exercise buried in `warmUp` will therefore never be progressed, never be audited, and never be counted — it is functionally frozen at whatever load it was written with.
  - **Live example (do not replicate):** Aimee Morris's Day A `warmUp` is now a single ~700-character paragraph holding 8+ separate drills, two of which are genuinely loaded exercises with rep prescriptions — "standing hip-hinge back fly 2×10-12 (light DBs...)" and "around-the-world lateral raise 2×10 (3-5 lb...)". Both are real accessory work with real load, and neither will ever be progressed where they currently sit. The drift is incremental and easy to miss: each revision appends one more useful thing to the string, and no single addition looks wrong.
  - **Check this on every revision, not just first build.** When adding content to an existing client's day, ask where it belongs before appending to `warmUp` — and if you're editing a day whose `warmUp` has already grown past a couple of sentences, that's the moment to promote the loaded items out of it into a proper block. Flag the promotion in your report; it changes the document's structure, not just its text.
- **Intake-pending clients are a distinct category with different build rules** (added 8/18/2026 — see `CLIENTS.md`'s "Intake Pending — Jason Bethea Clients" and `CLIENT_OPERATIONS.md` Sections 1a and 3a). Ten clients were added to the roster 8/18/2026 from Jason Bethea's SOAP-note archive. - **`client.sex` is currently INERT — it does not select a framework** (added 8/18/2026). Grep-confirmed: `scripts/icons_template.js` never reads `client.sex` anywhere. The women's Age Bracket Framework vs. the Male Client Programming Framework is selected **by hand, per script** — by which functions you call (`proteinTargets()`/`nutritionBlock()` vs. `maleProteinTargets()`/`maleNutritionNote()`/`testosteroneNote()`) and which thresholds you write into the document. Nothing in the data object enforces or checks that choice.
  - **The hazard is specific:** setting `sex: 'female'` in a `data.client` object *looks* like it gates something. It does not. A future script could set the field correctly, call the wrong framework's functions, and produce a document that is internally consistent, structurally valid, passes every audit — and applies the wrong sex's clinical thresholds throughout. Nothing would catch it.
  - **Treat the field as annotation-only for now** — useful as documentation of a fact for a human reader, and worth setting accurately for that reason, but never as a substitute for making the framework choice explicitly and stating it in the script's header comment (the Jake Poyner/Vinz Feller/Nick scripts are the reference pattern for documenting that choice in prose).
  - **Wiring it up is a real, worthwhile future engine improvement** — the natural switch point is `proteinTargets()` vs. `maleProteinTargets()`, with the same pattern extending to `testosteroneNote()` and the ALST threshold (<5.5 women / <7.0 men, which are currently applied by hand). That's an `icons_template.js` change, out of scope for a client build; flag it rather than implementing it mid-build. Note the field would also need a third state for the no-demographic-data case CLAUDE.md's Demographic Scope Rule now covers — an unset `sex` must not silently default to the women's thresholds.

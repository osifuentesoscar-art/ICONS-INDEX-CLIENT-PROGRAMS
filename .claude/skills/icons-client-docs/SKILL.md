# ICONS Client Documents

Every client deliverable at Brace Life Studios is generated by running a Node
script that calls the engine at `scripts/icons_template.js`. Nothing is ever
hand-authored as a `.docx`, because the engine is where the brand — page
geometry, the three-tier color system, table column widths, the auto-firing
clinical callouts — actually lives. A hand-built document looks approximately
right and is wrong in a dozen invisible ways.

| Deliverable | Engine function | Lands in |
|---|---|---|
| Training plan (trainer copy) | `buildDocument(data)` | `clients/<client_name>/<Name>_<N>Day_Training_Plan.docx` |
| Client View (client copy) | `buildDocument({...data, viewMode:'client'})` | same folder, `..._Client_View.docx` |
| Initial assessment report | `buildAssessmentReport(data)` | `clients/<client_name>/<Name>_ICONS_Performance_Assessment.docx` |
| Before/after progress report | `buildImprovementDoc(data)` | `clients/<client_name>/<Name>_Improvement_Report.docx` |
| Styku interpretation | *(no document)* | a written read-out in chat |

## Setup

The repo ships no `node_modules`. Before the first build in a session:

```bash
npm install                      # installs docx@^9
pip install python-docx --quiet  # needed for the audit step
```

## The pipeline

### 0. Read the client's record before writing anything

Open `clients/<client_name>/README.md` (the client's full record) and any existing
`scripts/<client>_*.js`. `CLIENTS.md` is only the roster index — it will not have the detail.
This is not ceremony — it is the step that catches the mistakes that actually
happen. A client often has more data on file than the current request mentions:
a tested baseline that belongs in `baselines[]`, a clinical constraint someone
established months ago, a Jason Bethea exercise that has to keep its prescribed
slot. Building only from what the prompt says is how a document ends up quietly
missing a section every comparable client has.

On a revision, also read the *previous* version of the script. Everything that
was not asked to change must not change.

### 1. Establish the demographic frame and the clinical flags

Do this before choosing exercises, because it decides which numeric thresholds
are even legal to apply. Read `references/clinical-frame.md` — it carries the
scan-reading procedure, the corrected thresholds, the protein and creatine
logic, and the three-case scope rule that governs male clients and clients with
no demographic data at all.

If the client's condition has no dedicated section in CLAUDE.md's science layer
(a new diagnosis, an unfamiliar population), say so and get research done before
finalizing. Shipping a clinical-sounding document with no grounding under it is
worse than shipping late.

### 2. Pick the document and read its reference

- Training plan or Client View → `references/training-plan.md`
- Assessment report → `references/assessment-report.md`
- Styku read-out with no document → `references/clinical-frame.md` alone

### 3. Write the build script

One script per client per program, at `scripts/<client_name>_<N>day_plan.js`,
following the shape of the closest existing sibling. Two reference builds worth
imitating directly:

- `scripts/siobhan_hansen_3day_plan.js` — the Block Method pilot. Full Styku
  data, ALST At-Risk, postmenopausal, real tested baselines driving
  `epley1RM()`/`workingLoad()`, both trainer and Client View written in `main()`.
- `scripts/rena_paul_assessment_report.js` — the assessment-report pilot,
  including the correct way to extend the default footnote set.

Open the script with a header comment explaining the clinical reasoning: which
bracket applies and why, what each flag is doing to the program, what was
deliberately omitted and on what grounds. This comment is the audit trail. When
someone asks in three months why a 45-year-old client has a pelvic floor
callout, the answer needs to be in the file, not in someone's memory.

Derive loads, never guess them:

```js
const oneRM = epley1RM(195, 5);        // 228
const wk1   = workingLoad(oneRM, 0.80); // 180, rounded to 5
```

### 4. Run it, then audit it

```bash
node scripts/<client_name>_<N>day_plan.js
python3 .claude/skills/icons-client-docs/scripts/audit_docx.py \
  clients/<client_name>/*.docx --expect "<Client Name>" "DAY 1" "<key lift>"
```

It extracts every paragraph and table cell, then reports template leakage
(`undefined`, `NaN`, `${`), possible leftover placeholders, and which clinical
callouts and standard sections it can find. It picks a training-plan or
assessment-report profile from the filename; override with `--type`, and add
`--compare <sibling.docx>` on a first build to catch a section a comparable
client's document has and this one is missing. Exit code 1 on a hard failure, so
it can gate delivery.

Run it on every file you generate, including the Client View — a bug that only
affects the client copy is the worst kind, because that is the copy that leaves
the building.

`soffice --headless --convert-to pdf` is broken in this environment on
known-good files. Don't spend time on it; structural verification is the
substitute.

Fix what the audit finds by editing the build script and re-running — never by
patching the `.docx`. The script is the source of truth; a document that has
drifted from its script cannot be regenerated.

### 5. Deliver

Send the finished files with `SendUserFile`. Do **not** upload to Google Drive:
`mcp__Google_Drive__create_file` silently corrupts files above ~26 KB and the
integration has no delete, so a failed attempt leaves a permanent orphan. Xolokan
uploads manually. Offer the Drive filename convention alongside the file —
`<ClientName>_<ProgramTitle>_YYYY-MM-DD.docx` — noting that repo filenames stay
undated because git history is their versioning.

## Rules that hold across every document

**Never fabricate a number.** Not a "before" value for a comparison table, not a
1RM for an untested lift, not a Level rating, not a citation. Every figure in
these documents is read by a trainer who will act on it and by a client who
believes it. An honest "Not Tested Today" row is correct and expected; an
invented one is a clinical error that propagates into loads, into targets, into
the next rescan. If a value is missing, the document says it is missing.

The same applies to citations. The Assessment Report's footnotes are data, not
prose to be improvised — verify a source independently before citing it, even
one that arrived in a reference document from Xolokan. That exact check caught a
real problem during the pilot build.

**Apply only the thresholds validated for the client in front of you.** The
women's ALST, protein, creatine, LIFTMOR, and pelvic floor numbers do not
transfer to a male client, and neither framework covers a client with no age or
sex on file. `references/clinical-frame.md` has all three cases. The failure
mode here is silent — a number that looks authoritative and was derived from the
wrong population.

**Let the engine fire its own callouts.** `buildDocument()` inserts
`proteinBar()` automatically whenever `client.alstIndex < 5.5`, and
`pelvicFloorCallout()` whenever `client.isPostmenopausal` is true and the day
contains a squat, deadlift/RDL, hip thrust, carry, or lunge. Calling them by
hand duplicates them. If one is missing from the output, the client data object
is missing a field — that is the bug, not the engine.

**Generate the Client View alongside every training plan, every time.** Not just
on first build — on every later revision too. Both copies come from the same
`data` object and the same `buildDocument()` call, which is precisely what stops
them from drifting apart.

**Program against the real studio inventory.** Dumbbells stop at 60 lbs/hand and
kettlebells at 25 lbs; loads past those move to the Olympic or hex bar. The
Kieser line serves as the studio's cable machine. Virtual and home-gym clients
program against their own equipment instead. Full list in
`references/training-plan.md`.

**Don't change the engine while building a client document.** If
`icons_template.js` is genuinely missing something you need, say so and work
around it in the client's script — a build is the wrong moment to alter the file
every other client's document renders through, and an engine change made in
passing gets no review and no regression check against the rest of the roster.
The same goes for the delivered `.docx` of a client you weren't asked to touch.

**CLAUDE.md wins on conflict.** These reference files compress its science layer
into build-time decision tables; CLAUDE.md remains authoritative and carries the
citations and the reasoning. If the two disagree, follow CLAUDE.md and flag the
drift so the skill can be corrected.

## Reference files

- `references/clinical-frame.md` — reading a Styku scan, corrected thresholds
  (ALST, VFA, BMI, asymmetry), protein and creatine, the demographic scope rule,
  and which callouts fire from which fields.
- `references/training-plan.md` — the `buildDocument()` schema, the ICONS Block
  Method, the Antagonist Rotation Rule, the intensity framework, load and
  progression conventions, Client View filtering, studio equipment.
- `references/assessment-report.md` — the `buildAssessmentReport()` schema, its
  helper functions, the footnote system, and the rules specific to that document
  type.
- `scripts/audit_docx.py` — structural verification for any generated `.docx`.
